# DAIINAS v4.3 — Cloud-first runtime and phone-based remote operations

**Owner's architectural insight (2026-11-01):** If KuCoin is a web service and Codex develops remotely, the owner should not need a powered-on personal computer. This is achievable if DAIINAS itself runs as an independently hosted, persistent cloud service, and a mobile phone supplies authenticated operator commands. The owner previously discussed a local-PC 24/7 setup; that is now an **optional fallback**, not a mandatory condition. No hosting provider has yet been selected, funded, deployed or connected. Do not claim Codex Cloud itself is the permanent execution host.

## Three separate responsibilities, no category confusion

1. **Codex + GitHub = SOFTWARE DEVELOPMENT.** Codex Cloud runs task-scoped coding work in isolated environments and must not be relied on as a production trading daemon. It may build/test a release; continuous operation requires a separate supported runtime.
2. **Cloud runtime = LIVE PROCESS.** Deploy DAIINAS Python market scanner, event-sourced risk/portfolio/Capital Ladder, reconciliation, scheduler and state store on an always-running provider. Possible managed PaaS choices include Railway persistent services, an approved equivalent managed worker platform, or a VPS. Prefer managed hosting over self-managed VPS only if long-running WebSocket, durable encrypted volume/database, restart behavior, provider IP restrictions and security can be demonstrated. No provider choice by implication.
3. **KuCoin = EXCHANGE EXECUTION / CUSTODY.** Public and authorized private WebSockets/REST provide market and account state; exchange-native protective/conditional orders can survive a disconnected bot once accepted by the exchange, subject to contract support and possible rejection/nonfill. The exchange does not autonomously run custom DAIINAS market intelligence.
4. **Phone = CONTROL ROOM.** Secure mobile HTTPS interface shows current account/position state and commands START/PAUSE/DISARM/STATUS. DAIINAS remains operative with phone off. Codex phone/cloud tasks can update code but are not automatically authenticated actions on the running exchange-control service. To control DAIINAS directly through ChatGPT/Codex would require a separately built and authorized control integration; until then use the phone dashboard.

## Required daemon / control state model

Persist separate operator **DESIRED_STATE** and actual process **OBSERVED_STATE**, along with UTC timestamp, actor identity, audit event, version and selected exchange account. A worker restart cannot be interpreted as approval of new trading permissions.

DESIRED_STATE: READ_ONLY | ARMED_PAPER | AUTO_AUTHORIZED_ELIGIBLE_SPOT | PAUSE_NEW_ENTRIES | DISARMED. The actual live-order mode is **DISABLED** until owner-approved release and eligible Spot product controls pass; the interface may show that mode as unavailable, never enable it based on a generic START command.

OBSERVED_STATE: OFFLINE | STARTING | RECONCILING | HEALTHY_READONLY | PAPER_ACTIVE | AUTO_ACTIVE | PAUSED | DEGRADED | EXTERNAL_INTERVENTION | HALTED_RISK. An operator START is a **request**; it never skips KuCoin snapshot, current wallet account mode, permissions, live order/fill/reconciliation, orderbook, available balance, protected reserve and strategy validations. A successful acknowledgement should say 'requested, pending reconciliation' until actually active.

**START:** authenticated command changes desired state; after synchronous durable authorization + risk/capability preflight, worker may begin paper trading, or later separately authorized live eligible Spot order proposals. Cloud reconnect and physical phone presence irrelevant.
**PAUSE:** block new positions immediately (and preferably pending nonessential new orders when owned/approved), preserve all open-position monitoring, source ingestion, protective stops, account sync and unresolved exits; distinguish paused from flat.
**DISARMED/STOP_STRATEGY:** disallow new entries persistently across restarts. Does NOT silently close or cancel existing exchange positions; show explicit open exposure. A separate highly privileged `REQUEST_RISK_REDUCTION` or `CLOSE_OWNED` command may be designed for a future approved execution gateway; never cancel or close someone else's Bitsgap/manual position by default.
**EMERGENCY_DISABLE:** revoke automation entry authority and latch HALTED_RISK. If runtime is unreachable from phone, operator must have a documented direct KuCoin/manual contingency; cloud control UI cannot ensure immediate action if its server is down.
**Cloud/process outage or provider restart:** detect interrupted worker; restart policy; reacquire **single-leader** lease; before any planned new-entry action, re-fetch complete account balances, orders (including conditional orders), fills, positions and mode, compare durable event log and dedupe by clientOid. Maintain exact-once financial application; a timed-out order submission must be queried by clientOid, never blindly retried. After restart, resume automatic entries ONLY if separately enabled prior authorization permits that behavior **and** full reconciliation + all gates succeed. Else remain PAUSED. An uncategorized pending order or unknown external order => fail closed.
**Internet/exchange WebSocket outage:** stop new entries; never infer market fills/fees from stale marks. Exponential reconnect, REST backfill and consistency check; restored internet != restored safe trading.
**Database failure:** stop all new entries, preserve KuCoin-protective orders and raise out-of-band alert when possible; fail closed, no duplicate workers or orders, no trusting local stale cash.

## Failures, hosting and remote access

- Deploy one persistent always-running worker and **one** active order-writer per account. Persistent volume with correct SQLite WAL/snapshot backups may work for single-host pilot; for cloud failover/high availability prefer durable managed PostgreSQL and a transactional journal/outbox with single-leader fencing. Never pretend a Railway startup healthcheck continuously monitors a live service: Railway docs state deployment-only healthchecks; add application watchdog, independent uptime/error notifications and regular reconciliation jobs.
- Deployments/updates must coordinate old/new worker to prevent overlapping order writes; set startup desired_state to PAUSED/READ_ONLY unless pre-authorized safe auto-resumption has been implemented and tested.
- Avoid scale-to-zero, sleep-mode 'free' hosting and ordinary scheduled jobs for a process requiring constant private/public WS; demonstrate provider-backed persistence and expected restart/downtime behavior.
- Protect remote dashboard with HTTPS, strong independent authentication/passkey or MFA, session expiration, device identity/rate limiting, CSRF protection, least-privilege user roles, confirmation for higher-risk actions, immutable audit trail, no open unsecured webhook or API order command. Never use raw public bearer tokens or paste KuCoin API keys into ChatGPT/GitHub; secrets belong to hosting provider secret manager and be separated from dashboard login.
- Server location, outbound IP egress and KuCoin API allowlist must be checked. A cloud provider's changing outbound IP may conflict with exchange trading-key IP restrictions; choose supported static outbound IP/egress only if a future eligible trade interface needs it. No VPN/geo-bypass to evade rules.
- Owner can inspect KuCoin directly from phone independently of DAIINAS; KuCoin state, not dashboard beliefs, is authoritative for actual exposure. Manual/Bitsgap modifications reconcile before new entries.
- Secure backup and rollback: backups encrypted, restore tested, event ID/financial sequence invariant checked; secrets never in repo or exported reports. Strict permissions for any future private API credential.
- Outages are inevitable. Exchange-native accepted risk orders are desirable where supported but **NOT** a loss cap guarantee: conditional orders can fail to activate/fill under volatility, liquidity or insufficient funds. Model incomplete protection explicitly. No automatic cancel-on-disconnect if that would remove protection.

## Regulatory/product gate

UK retail offering of certain crypto derivatives is prohibited under FCA rules. A KuCoin Futures/Hedge interface being visible or API endpoint callable is not proof of legal eligibility. All live Futures/Perps hedge trading remains **BLOCKED** until independently verified product and jurisdiction eligibility. Only possible future **Spot** live execution may be evaluated after separate explicit authorization and a verified account/custody and security boundary. Never bypass country restrictions by third-party endpoints.

## Implementation and acceptance order

**Milestone A — architecture and PAPER control, ready for Codex:** one persistent cloud worker, durable task state and journal, `GET /status`, authenticated `POST /control/{start,pause,disarm}` (no live-order route), audit receipt, mobile-friendly UI and an independent access-control service. Test hosted worker survives user's own phone/laptop being off, network failures, bot restarts and redeploy; PAPER ONLY.
**Milestone B — real KuCoin read-only:** owner enters a new permitted `General` read-only API Key/Secret/Passphrase **only in the selected host's secret UI**, not in GitHub, Codex task logs or chat. Account mode discovery, initial REST snapshots, private WS, buffered order changes, deduplicated reconnect, reconciliation across manual/Bitsgap, and observable HEALTHY_READONLY status.
**Milestone C — operator-intervention tests:** remote PAUSE/START changes desired state durably and cannot claim success until worker acknowledges. Disconnect phone, restart worker, rotate versions, force WS gap, stale data, duplicated private fill, unknown open order, provider downtime and bot session expiry. Verify no unsolicited order or reserve use, nor loss of open positions from UI view.
**Milestone D — future execution gate:** only after paper alpha, audited Capital Ladder integration, documented spot product eligibility, exchange API trade permissions, security, external-audit and owner sign-off; real order routing separate and OFF by default. Future mobile STOP cannot remove exchange-native protective orders unless explicitly approved.
