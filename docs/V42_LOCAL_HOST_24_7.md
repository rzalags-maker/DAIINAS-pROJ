# DAIINAS v4.2 — Owner-selected LOCAL 24/7 hosting (P0)

**Owner deployment decision, 2026-11-01:** DAIINAS will run continuously on the **owner's own computer**, NOT an external VPS or third-party cloud host. KuCoin API connections originate from that local computer's network. The operating system and its version have **NOT YET BEEN CONFIRMED**. Do not invent Linux/VPS requirements or assume the user's old Mac Pro experiments are the execution host.

## Local process architecture

1. Run one unprivileged background DAIINAS service using the installed OS service manager: macOS `launchd`, Linux `systemd --user`/system service, or Windows Task Scheduler/Windows Service. **Select only after detecting the operating system**; ship separate examples rather than blindly installing all three. Do not assume launching when a user logs in is reliable when the user is logged out; choose automatic start at machine boot for unattended 24/7 service when appropriate.
2. Local encrypted OS credential vault: macOS Keychain, Windows Credential Manager/DPAPI, or an appropriately secured Linux secret store. Do not embed KuCoin Key, Secret, Passphrase in source, git, argv, logs, CI, shell history, screenshots, SQLite or unencrypted startup scripts. The user enters credentials **locally** into a private setup interface; Codex has no legitimate need to see the secret values. Verify key permissions are `General` read-only first. Do not silently switch to a trading-capable key.
3. Public KuCoin REST/WS should already function without private credentials. Implement actual private read-only authentication as a separately gated module and verify current account type, supported KuCoin API version and account scopes before syncing. Current KuCoin docs https://www.kucoin.com/docs-new/authentication and https://www.kucoin.com/docs-new/ .
4. On boot: read local encrypted configuration -> validate host time/UTC drift and credential availability -> CONNECT PUBLIC -> PRIVATE READONLY -> obtain complete balances/orders/positions/fills snapshots with event buffering -> reconciliation -> `RECONCILED_READONLY`. Only the last state may be displayed as synchronized. A valid key alone is NOT evidence of complete account state.
5. Keep exactly one SQLite single-writer service per account ID and distinct v3.3 vs v4 database paths, file locks and backups. Use transactional WAL/recovery where appropriate, idempotent event IDs and ordered durable journal; on power outage, partial transaction, unexpected kill or machine restart, **replay/reconcile** rather than reinitialize capital, duplicate fees or send fresh orders. Backups use SQLite backup API or an equivalent consistent backup method; copying only an in-use `.sqlite3` without WAL is insufficient.
6. Connectivity: HTTPS outbound to official KuCoin REST domains and outbound WSS to the official server returned by the appropriate private/public endpoint; no inbound port forwarding or public web server needed for standard connectors. Network reconnect with exponential backoff+jitter, heartbeat watchdog and gap detection, independent of chart rendering. Avoid leaking auth data into telemetry or URLs. Respect KuCoin rate limits.
7. If the home broadband external IP changes, keys with configured IP allowlists may fail. Before connecting, **inspect actual KuCoin API key restrictions**. With `General` read-only, the official guide says the key is not subject to the same 30-day rule as unrestricted trading keys; do not claim a static IP is mandatory for General access. For future order permissions, require documented KuCoin IP allowlist policy and a stable verified network path — never disable exchange security restrictions for convenience or assume a home address has static IP.
8. Local monitoring: last successful public quote, private WS heartbeat, final REST reconciliation time, data-gap count, authentication failures, available disk space, clock skew, SQLite write errors, detected manual/Bitsgap interventions, current active/reserve/pending and outside liabilities, open positions plus unknown orders. Watchdog must show `HEALTHY_READONLY`, `DEGRADED` or `OFFLINE`, with **no new automated entries** unless every gate is satisfied. Do not pretend that keeping a desktop powered on makes the strategy risk-free.
9. Operator control can happen on the same computer from a local-only dashboard bound to `127.0.0.1`, with CSRF/token protections as relevant. Remote dashboard/control is a separate future security review; never open all interfaces on `0.0.0.0` by default. Pausing entries must not stop market observation, existing risk monitoring, read-only reconciliations or logs.
10. Shutdown/reboot: persist clean checkpoint, stop new entries, reconcile source cursor; on crash recover from SQLite and verify against real KuCoin order state BEFORE any future live execution. If no private credentials, keep public feed and independently labelled PAPER mode functioning with actual-balance status `NOT_CONNECTED`.

## Security and deployment constraints

- First KuCoin private phase is **General READ-ONLY**; no actual orders, cancel requests, transfers, withdrawals, account-mode changes or leverage mutations. Actual Spot trading requires separate owner approval, key permission, eligible product and tests; UK retail Futures/Hedge remains blocked absent independently verified eligibility.
- A previously screenshot-visible complete secret, if exposed, must be rotated; key age is not the threat, secret disclosure is. Never send secrets into chats or GitHub.
- Full-account observation requires the correct account class (Classic Spot, Classic Futures, UTA) and authorization, and may not include unrelated wallets or assets. Some private endpoints can reject requests due to account/region restrictions; report accurately.
- Background power options: prevent system sleep for the designated host while preserving lock screen and necessary security updates; monitor home power/internet interruptions, disk health and OS restart policies. Strongly recommend battery backup if unattended exposure becomes approved in the future, but do not imply it already exists.

## Must-pass acceptance tests

1. Local service fixture auto-start/restart with OS-appropriate mechanism (only once host OS known), no terminal kept open, no unintentional duplicate worker.
2. All credentials are provided only by the local OS secret vault and never appear in crash reports, logs, repository, CLI args or CI artifacts.
3. Public data remains usable with private endpoint disconnected; private state explicitly `NOT_CONNECTED`, not assumed empty or 8 USDT.
4. Cold read-only connection discovers mode and snapshots complete open orders/positions/balances/fills; manually modified and Bitsgap/unknown orders force safe reconciliation without fabricated actor attribution.
5. Simulated network outage, router restart, dynamic IP allowlist mismatch, PC sleep, unclean process stop and power loss cause DEGRADED/OFFLINE, safe backlog replay and idempotent recovery; no invented fills or new entries.
6. Verify local database backups and restore, protection of reserve, correct external deposit provenance and no wallet double count.
7. Demonstrate local startup and end-to-end read-only observation on owner's machine after operator provides private credentials in OS vault. This cannot be genuinely claimed without that machine/runtime access; GitHub Actions mock success is insufficient.
